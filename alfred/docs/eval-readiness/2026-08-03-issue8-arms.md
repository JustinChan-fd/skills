# jarvis#8 — two-arm comparison, leak audit first

## Why this file exists

The run before this one (`20260803T172738Z-6`, jarvis#6) was **void**, and not for a
reason the record could show. `main:src/components/ui/textarea.tsx` already read
`min-h-20 md:min-h-32 ... text-sm` — which *is* the fix the ticket asks for. Two prior
branches had made that change, one of them (`jarvis-6-fix-textarea-mobile-scale`) is on
the **remote**, and `gh pr list` returns PRs **#9 and #10** titled
`fix(issue-6): textarea min-height responsive on mobile`.

So the worker spent 33 tool calls and ~$1.32 hunting for a viewport test seam that this
repo does not have, because there was **no code change left to make**. The trace looks
like thrashing; the cause was a ticket that was already satisfied.

The diagnosis matters more than the waste. My first reading of that trace was "the ac_map
contract is distorting the work" — the worker chasing a verifiable command instead of
writing the fix. That was wrong, and it was wrong in the direction that would have led to
editing `gate.mjs`. Checking `main`'s file contents before theorising would have settled
it in one command. **A contaminated ticket produces a trace that mimics a harness defect.**

Hence: the audit runs BEFORE the arms, and its result is written down. An isolation claim
nobody recorded is an isolation claim nobody can check.

## The four leak channels

A prior attempt is reachable four ways, and a fresh branch closes **none** of them:

1. `git log --all` / `git show` — sees every local ref
2. `git ls-remote` / `origin/*` — sees every pushed branch, so a clone is not enough
3. `gh pr list --state all` — sees **closed** PRs, which is how #6 leaked hardest
4. `main` itself already containing the change — the one that voided #6

Worktrees share the object store and the remote, so channels 1–3 stay open under
worktree isolation. That is acceptable **only** when the audit shows there is nothing
to find. It would not be acceptable for #6 on any branch, in any worktree, in any clone.

The last row is the one worth keeping. A branch existing is not contamination; a branch
holding an *unmerged answer* is. `git merge-base --is-ancestor` is what tells those apart,
and the ticket asking you to reuse the merged work makes it context rather than a leak.

what an operator can reproduce without git. **The property the comparison actually rests on
was verified directly and independently of any recorded digest: the two arms' configs are
byte-identical to each other** (`cmp` clean), which is the claim, rather than either one
matching a number written down earlier.

## What this comparison can and cannot settle

**Can**: cost per arm, whether the gate's verdict tracks the work, whether `deliver`
reaches push + `gh pr create --draft` — which has never executed against a real remote,
because the gate has never returned `true`.

**Cannot**: anything about `mapping_implausible`'s false positive on jarvis#11, which is a
separate, already-measured defect. There, the gate failed a run that had **delivered
working code** (`56162bc`, 5 files, 131 insertions) because the ac_map command shared no
subject word with the AC:

```
AC6 words:  clear data contract operation set defines relationship notes todos context consistent
cmd words:  npx vitest run server tests summarize test explicitly lists completed tasks
            instructs model exclude them from pending sections
overlap:    ['the', 'and', 'the']   → stopword-filtered to nothing
```

The rule measures vocabulary overlap and reports it as relatedness. Naming a test by its
`-t` description rather than by the AC's own words is enough to fail it. That is a real
finding and it is **not** what these arms are testing — recorded here so the two do not
get conflated when the results land.
